## Problem Statement

在闲置 Android 手机上运行一个本地 AI 双色球工具：多策略同场竞技、每期自动对账、诚实呈现「任何算法（含端侧 LLM）能否打赢纯随机」。定位是黑客松级观赏性 + 开源研究本地 AI 能力边界。原始诉求「彩票投资收益最大化」已在会话中改写为「诚实实验 + 统计娱乐」（用户明确同意）。

## What Makes This Cool

- **LLM 是实验对象，不是神谕**：MiniCPM5-2B 以多 persona 参赛，MiniCPM-V-4.6 用视觉语义选号，全部与纯随机对照组同台被检验。
- **走前回放**：20 年历史（约 3300 期）一晚跑完赛季，不用等开奖攒数据；「等两年」变「今晚出判决」。
- **零后端农场（v2）**：每台手机一个策略，每晚推 JSON 到 git 分支，GitHub Actions 聚合、Pages 大屏，git history 天然防篡改。
- **旋转矩阵**：真实的组合数学（覆盖设计），前提成立时给出保底命中结构——「科学的缩水」有可验证的数学内核。

## Constraints

- 宿主工程：Scrapbook4Android（AGP 7.4.2 / Gradle 7.5 / JDK 11 / Kotlin），新 module 不得破坏现有 app/lib_base/lib_stock/lib_views 构建。
- 算法蓝本：`lotterylab`（Python，七阶段 pipeline：fetch→cache→analyze→pool→shrink→verify→export；策略 frequency/cold_hot/missing/matrix + filter）。路径（2026-10-02 确认）：`D:/gitprojects/devtoolslab/x-projects/pythonlab/lotterylab`（`data/lottery.db` 434KB 在位，导出步骤可行）。
- 端侧推理蓝本：`MiniCPM-V-demo-Android`（`LlamaEngine.kt` llama.cpp JNI、`ModelDownloadService`、`VideoFrameExtractor.kt`、TTS）。路径（2026-10-02 确认）：`D:/gitprojects/devtoolslab/x-projects/androidlab/MiniCPM-V-Apps/MiniCPM-V-demo-Android`（jniLibs 实测仅 arm64-v8a，佐证 D16 基线）。
- 模型：MiniCPM5-2B（纯文本，官方 GGUF + 官方 llama.cpp 部署文档）+ MiniCPM-V-4.6（~1.3B 多模态，GGUF 量化版已存在）。
- 数据源：datachart.500.com 公开历史页（lotterylab 已验证抓取）。

## Premises（用户已逐条同意，2026-09-27）

4. 工程：Kotlin 重写核心算法，独立 module，兼容 AGP 7.4.2/JDK11。

## Approaches Considered

### Approach A: 周末判决书（纯 JVM 回放引擎）
S / Low。最快拿到带 p 值的判决表；无手机画面无 LLM，观赏性为零。**未选：观赏性诉求缺席。**

### Approach B: 端到端手机竞技场（Android 优先）
L / Med-High。一步到位；JNI+模型+抓数风险并行叠加，第一个可展示物最晚出现，核心逻辑被 AGP 绑架。**未选：重构税与风险叠加。**

### Approach C: 双级火箭（JVM 内核 + Android 壳 + git 农场骨架）✅ 已选
M / Low-Med。第一阶段就是 A 的全部，但模块从第一天分两层；农场协议接口层预留。

## Recommended Approach: C —— 完整需求与设计

### R1. 模块结构（第一天就分两层）

```
lib_lottery_core/   # 纯 JVM Kotlin（kotlin("jvm")），永不 import android.*
  domain/           # Draw, NumberPool, BetScheme, BetPlan, PrizeTable, LedgerEntry
  strategy/         # Strategy 接口 + 6 个 JVM 内置实现
  replay/           # WalkForwardReplay, NullDistribution(1000次随机), PValue
  arena/            # SeasonRunner: 每期调度全部策略 → 出票 → 对账 → 聚合
  data/             # CSV 解析 (ssq_history.csv), DrawRepository
lib_lottery/        # Android 壳（AGP module），依赖 core
  infer/            # LlamaEngine JNI 移植, ModelDownload 移植, GGUF 资产管理
  strategy/         # LlmPersonaStrategy, VlmImageStrategy, CameraSeedBytesProvider(相机取字节 provider)
```

模块归属（一句话定论）：PixelSeed 的**确定性出票逻辑在 core**（6 个 JVM 实现之一，种子字节经 PickContext 注入）；lib_lottery 只放相机种子字节 provider（拍照→字节）。

`settings.gradle` 增加 `include ':lib_lottery_core', ':lib_lottery'`。core 的 JVM 测试秒级运行。lib_lottery 沿用宿主 `rootAndroid`（minSdk 21 / compileSdk 34，见 config.gradle）；core 为纯 JVM 无 minSdk（工程评审更正 2026-09-27）。Kotlin 1.9.21 / AGP 7.4.2 / Gradle 7.5，`kotlin('jvm')` module 与宿主 buildscript 风格兼容。

### R2. 领域模型（对齐 lotterylab/models.py 的不变量）

- `Draw(period, reds: SortedSet<6>, blue, date, source)`：红 1-33 不重复已排序，蓝 1-16。
- `NumberPool(redPool, bluePool, strategyName)`：红池≥6、蓝池≥1。
- `BetScheme(reds×6, blue)`、`BetPlan(schemes, totalCost = schemes×¥2, generatedAt, config)`——构造即校验，非法抛 `IllegalArgumentException`，与 Python `__post_init__` 行为对齐。
- `PrizeTable`：三等奖及以下固定金额；一/二等奖浮动，回放按 500 万/15 万假设并在账本显著标注「假设值」。

### R3. 策略接口与竞技场阵容

```kotlin
interface Strategy {
    val id: String; val displayName: String
    val requiresModel: Boolean      // false=纯JVM可跑, true=需端侧模型(Android)
    fun pick(ctx: PickContext): BetPlan   // ctx 含 history(截至t-1), rng, params
}
```

| 选手 | 实现 | requiresModel | 每期注数 |
|------|------|---------------|----------|
| 纯随机（对照组）| 均匀采样 | 否 | 1 |
| 频率派 | 频率加权采样（lotterylab frequency 移植）| 否 | 1 |
| 冷号猎手 | cold_hot 移植 | 否 | 1 |
| 遗漏保守派 | missing 移植 | 否 | 1 |
| **旋转矩阵** | matrix 移植（见 R4）| 否 | ≈25 |
| PixelSeed | 种子字节 SHA-256 → kotlin.random → 确定性出号 | 否（种子字节由平台提供：Android 相机照片 / JVM 打包资产照片）| 1 |
| LLM 人格 ×3 | MiniCPM5-2B 读统计 JSON 出号+流式理由（N=3 为 MVP 默认，配置可调）| 是 | 各 1 |
| VLM 读图 | MiniCPM-V-4.6 看图/视频帧 → 选号偏好 | 是 | 1 |

默认阵容 10 位选手：6 纯 JVM + 3 LLM 人格 + 1 VLM。JVM 回放中 requiresModel 策略缺席（赛季记录缺席原因），Android 实机全量参赛（仅 live-forward，见 R7）。

### R4. 旋转矩阵策略（用户点名，一等信息）

**语义（移植自 `rotation_matrix.py: generate_virtual_wheeling_system`，逻辑不变）**：用户选 n 个红球，预设「中 P 保 T」——若开出的 6 个红球全部落在你 n 个号中的某个 P 子集里（前提），则保证至少一注与该前提交集 ≥ T。实现：位掩码（Long，n≤33）+ 前提组合（P-subsets）全覆盖贪心选择（每轮选覆盖剩余前提最多的候选注），n==6 特判短路。

**默认预设（用户需求）**：12 红 + 1 蓝，目标缩水到约 25 注 = ¥50/期（对比全组合 C(12,6)=924 注）。P/T 取值实现期用回放校准（起点 P=7,T=4），验收断言：① 全部前提场景被覆盖（测试硬断言）② 注数落在 [20,30] 区间且成本 ≤ ¥60（目标 25 注/¥50）③ 蓝球池全配对（1 个蓝球即 25 注 ×1）。

**竞技场接入**：matrix 是 pool→shrink 的组合策略——每期先由频率派产出 NumberPool，matrix 消费它缩水成 BetPlan；独立记分。保留 lotterylab 的链式能力（matrix→filter：奇偶比/大小比/和值/连号过滤）作为高级配置。

**诚实边界（写进 UI 与 README）**：旋转矩阵是真实的覆盖设计数学，但它改变的是**前提成立时的命中结构（方差形状）**，不改变期望值。「12 个号包住 6 个中奖号」这个前提本身仍是运气。

### R5. 回放引擎与诚实账本

- `WalkForwardReplay`：期 t 时策略只见 [0, t)，出票 → 兑奖 → 入账。确定性：固定种子，快照测试断言同种子同结果。
- 冷启动规则：统计策略（频率/冷热/遗漏）在历史 < 30 期时回退均匀采样——从第 1 期起确定可复现。
- `NullDistribution`（按注数匹配）：每策略用**同注量**的 1000 次纯随机全赛季回放构造自己的零假设——1 注/期策略用 1 注/期 null，matrix 用 ≈25 注/期 null（注量不同则 ROI 方差形状不同，单一带宽 null 会给出失真的 p 值）；比较 stake-normalized ROI 的双侧经验分位。同注量、同期数、同弃权结构的零分布数学上同分布：JVM 回放中 1 注/期策略共享同一份 1000 次零分布，按（每期注数, 期数, 弃权结构）缓存；matrix（≈25 注/期）与含弃权的 live horizon null 独立构造（工程评审 C2 澄清 2026-10-02，输出语义不变，省约 5 倍计算）。
- 判决规则：双侧，单策略 α=0.05；多重比较校正**绑定报表阵容而非计算场所**——任何同时判决 K 位选手的报表统一用阈值 α/K，每张已发布报表固定一个 K（第一周 JVM 判决表 K=6 → α/6≈0.0083；实机全阵容报表 K=10 → 0.005），同一数据在 JVM 与 Android 上算出的徽章必须一致。1000 次零分布的经验分辨率下限 p≈0.001，报告为 "<0.001"。徽章：「与随机无显著差异 / 显著更差 / 显著更好（出现即数据问题警报）」。
- 模型选手（live-forward）判决规则：live 期数 < 30 时账本只报 ROI/命中分布并显示「样本不足，暂不判决」；≥ 30 期后用 horizon-matched null——1000 次与该选手**同长度、同每期注数、含弃权结构**的随机赛季构造零假设；弃权期按 0 注计（有效投入下降），null 同步含弃权。
- 账本字段：累计投入 / 累计中奖 / ROI / 命中分布（6+1…0+0）/ p 值 / 判决。一等奖按 500 万、二等奖按 15 万假设值计。

### R6. 数据

- 首发：历史数据在 lotterylab 的 SQLite 缓存（`data/lottery.db` 表 `draw_results`），用 `sqlite3 -header -csv` 单行命令导出 `ssq_history.csv`（约 3300 期）——lotterylab 的 export 阶段只导出投注 JSON，不产出历史 CSV（工程评审更正 2026-09-27）。schema: `period,red1..red6,blue,date,source`。打包位置（评审 D11=A，2026-10-02）：唯一副本置于 lib_lottery_core/src/main/resources/ssq_history.csv，core 测试与 Android 壳均走 classpath 读取，DrawRepository 封装 ClassLoader；不做 app assets 副本。
- MVP 期结果导入（手机侧闭环，不依赖抓取）：① 应用内手动录入开奖号（6+1 数字键盘；评审 D14=A 增补 2026-10-02：录入确认回显排序后 6 红+1 蓝；结算前可作废重录、结算后不可变；侧载 CSV 与已结算期不一致时告警且只追加新期）② 侧载替换 CSV 刷新历史；后续 on-device 抓 500.com（WorkManager + 增量），抓取失败不破坏已有赛季数据。
- PixelSeed 回放种子链：打包资产照片字节 → SHA-256 → 赛季种子 → 每期 seed = hash(赛季种子 ‖ 期号)（全赛季确定性可复现）；实机默认一季一照片，可选每期重拍。

### R7. Android 壳与端侧 AI

- 模型策略（LLM 人格/VLM）**仅 live-forward 参赛**：历史回放由 JVM 层覆盖，不做端上 3300 期模型回填（后续可选「末 50 期回填」作为显式实验开关）。
- 持久化：`filesDir/seasons/<season>/` 下按期 JSON（票据+理由+对账）+ 账本聚合 JSON，MVP 不引 Room；模型下载状态与偏好存 DataStore；进程重启后从文件恢复赛季。
- `LlamaEngine` JNI 封装从 MiniCPM-V-demo 移植（llama.cpp + GGUF）；`ModelDownloadService` 移植改造：MiniCPM5-2B Q4（约 1.5GB）与 MiniCPM-V-4.6 GGUF(+mmproj) 两个模型槽位，断点续传，用户主动触发。
- LLM 人格：统计 JSON → persona 提示词 → 流式输出 → **结构化出票**（要求 JSON 票据格式，解析失败重试 1 次后弃权并记录——弃权也是实验数据）。
- VLM 读图：照片或抽帧 → 视觉描述 → 映射为红/蓝区权重偏好 → 出号。输入节奏：live 模式默认**每个开奖夜一张用户拍摄照片**（相机或相册，与 PixelSeed 的种子照片相互独立），可配置为整季复用一张；回放/重播模式用打包资产照片。研究任务（冷读采纳）：同图 N 次采样分布 + 跨图分布对比（熵纯度实验室，二期）。
- PixelSeed：相机拍照 → 字节 SHA-256 → 确定性种子。同一张照片永远同一组号（卖点级交互）。
- UI 三屏（线框见文首路径）：竞技场卡片网格（对照组固定末位）/ 诚实账本（p 值列 + 「与随机无差异」徽章 + 免责声明）/ 开奖夜（LLM 流式解说 + 锁定状态 + 手动录入开奖号入口；演示时可用「重播模式」跑历史期）。
- 运行时完整性约束（工程评审增补 2026-10-02：D12/D13/D16=A + A4 注记）：**settle gate** — `SeasonRunner.settle(period)` 前置为该期在场选手全部出票或显式弃权，按期 JSON 断言 `pickAt < enteredAt`，违例 fail loudly，UI 拒绝结算并列出未完成选手；**模型校验** — 下载清单 JSON 附每文件 size+SHA-256，校验失败删除自动重下；**ABI 基线** — llama.cpp .so 仅打包 arm64-v8a，非 arm64 设备 requiresModel 策略显示「设备不支持」而非崩溃；**内存调度** — 同一时刻至多一个模型常驻，LLM 人格 ×3 复用同一 LlamaEngine 实例（换 persona 只换 prompt），VLM 与 LLM 分时加载。

### R8. 农场协议（v2 预留，接口层设计）

### R10. 工程与质量

- core 纯 JVM：`./gradlew :lib_lottery_core:test` 为 CI 门禁（快速单元测试，秒级——不含全量回放）。
- 关键测试：矩阵全覆盖断言（R4）、模型校验不变量、回放确定性（同种子同账本）、p 值计算对零分布的正确性、CSV 解析边界（缺列/越界号/乱序期号）、冷启动回退确定性。评审增补（2026-10-02）：PrizeTable 九级命中边界、策略权重生效统计断言、PixelSeed 种子链、settle gate（D12=A）、账本 30 期判决切换与弃权计 0 注、DrawRepository 资源缺失报错路径、null 共享缓存键等价；壳层 androidTest（D17=A）：赛季持久化+进程重启恢复、settle gate 拒绝/放行、录入确认/作废重录状态机、侧载 CSV 冲突守卫、模型清单校验（小文件假模型）；LLM persona fixture 语料解析成功率套件；三屏 UI 与流式走手工演示脚本。
